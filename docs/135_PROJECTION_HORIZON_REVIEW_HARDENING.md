# Projection Horizon Review Hardening

Status: closed

## Scope

This review closes the confirmed findings for:

```text
apps/api/internal/projectionintelligence/projectionhorizon
```

The implementation also hardens the HTTP and production consumers that accept or
use Projection Horizon plans.

## Accepted findings

- `Step` did not consistently mean an exact fixed grid because an unaligned final
  endpoint could be appended separately.
- Public `Plan` values could be manually assembled without a canonical validation
  boundary or complete invariant verification.
- The default horizon duration existed in configuration but was unreachable through
  the production HTTP read path.
- Baseline and historical continuation fingerprints represented only part of the
  horizon semantics and did not bind requested duration or truncation evidence.
- A nil policy returned an unrelated maximum-point-count error.
- Policy names were not required to be normalized and non-empty.
- Configuration could imply excessive schedule allocation or unsafe point-count
  conversion without a package-wide supported limit.
- Alternative horizon planners could return malformed plans that consumers accepted
  without validation.
- Regression tests and permanent Continuous Integration enforcement did not protect
  these contracts.

## Corrected contracts

- Projection Horizon advances to `projection-horizon-policy-v2`.
- Minimum, default, maximum, requested, and effective durations must align exactly
  with the configured fixed step.
- Forecast times are generated by indexed multiplication and form the exact sequence
  `AsOfTime + (index + 1) * Step`; no separately appended endpoint is permitted.
- `Plan.Validate` enforces version, normalized policy identity, canonical Coordinated
  Universal Time, duration relations, truncation relations, point count, exact grid,
  endpoint equality, and fingerprint integrity.
- `FinalizePlan` is the canonical finalization boundary and returns a defensive copy.
- The plan fingerprint uses SHA-256 and binds policy version and identity, as-of and
  end times, step, requested and effective durations, truncation evidence, point
  count, and every forecast time.
- Baseline and historical continuation fingerprints consume the canonical horizon
  plan fingerprint instead of maintaining incomplete duplicate horizon hashing.
- Missing `duration_seconds` now reaches the configured default duration through a
  zero-value internal boundary sentinel; an explicitly invalid duration remains
  rejected by the read policy.
- Policy configuration validates the normalized name, exact configured grid, point
  count, and a package-wide maximum of ten thousand forecast points before schedule
  allocation.
- Nil policy use returns the dedicated `ErrPolicyUnavailable` lifecycle error.
- Baseline, historical continuation, and production composition reject invalid plans
  returned by alternative planner implementations.
- Targeted, race, full-suite, vet, and permanent audit verification protect these
  contracts.

## Qualified or rejected findings

- `New(Config) (*Policy, error)` continues to return `nil` with an error when
  construction fails. This is idiomatic Go construction behavior and is not a domain
  null-state defect.
- Public `Plan` fields are retained for compatibility with existing internal
  producers and fixtures. `FinalizePlan`, `Validate`, defensive cloning, and consumer
  validation provide the required integrity boundary without a broad unrelated
  migration.
- Zero requested duration is retained only as an internal default-selection sentinel.
  `BuildDefault` exposes an explicit default construction path, while negative,
  below-minimum, and off-grid requests remain invalid.
- `Policy.Config` continues to return the zero configuration for a nil receiver. No
  caller relies on a typed error from this read-only accessor, and changing its
  signature would create unrelated migration work.
- Source-file length alone is not classified as a defect. The review required clear
  responsibility boundaries and invariant protection, not an arbitrary line-count
  target.

### GFA-DATA-319 — Projection Horizon Step did not define one exact fixed grid

1. **Finding / symptom:** `Step` could produce regular points and then append a separately aligned final endpoint, so it did not consistently define the full schedule.
2. **Root cause:** schedule generation iterated offsets and repaired the endpoint after generation instead of defining all slots by indexed multiplication.
3. **Failure scenario:** requested/effective duration is not exactly divisible by `Step`; most points follow the grid but the final point uses a different interval.
4. **Impact:** projection point timing and horizon fingerprint semantics become internally inconsistent.
5. **Severity rationale:** **P1 retrospective** because the horizon schedule is a primary temporal identity consumed by all projection strategies.
6. **Existing guarantees violated:** fixed-step horizon, deterministic forecast slots, exact endpoint equality.
7. **Considered solutions:** append final endpoint; round duration; reject off-grid durations and generate indexed slots.
8. **Chosen remediation:** all configured/requested/effective durations must align exactly to `Step`; forecast times use `AsOfTime + (index+1)*Step` only.
9. **Why selected:** the contract becomes mathematically exact rather than repairing an inconsistent schedule after construction.
10. **Rejected alternatives:** rounding or endpoint append silently changes requested temporal semantics.
11. **Trade-offs:** off-grid requests now fail rather than producing a best-effort schedule.
12. **Regression tests / protection:** configured-grid and requested-duration tests; `projectionhorizonreviewaudit` forbids endpoint append behavior.
13. **Adversarial review findings:** zero requested duration remains only an internal default-selection sentinel, not an off-grid public duration.
14. **Remediation iterations:** engineering `7249aa7625dd306bbd769dade6ce3262edca01ab`; audit `d2bc87b07ea0eb6a0b9b25f0a1e3cb2cbc52cd1b`.
15. **Residual risks / limitations:** configured fixed-step policy remains a product/model choice; this finding concerns consistency, not scientific horizon selection.
16. **Operational/deployment consequences:** invalid off-grid configurations/requests fail before schedule construction.
17. **Exact evidence:** review doc, implementation/audit commits, exact run `30402249129` SUCCESS, fixed-grid tests/audit.
18. **Final canonical status:** **CLOSED**.
19. **Prevention / future guard:** all horizon schedules must be generated from a single exact grid formula, never repaired with a special terminal point.
